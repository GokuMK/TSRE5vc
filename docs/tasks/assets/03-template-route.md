# Task 03 - Own Template Route

Status: ready; not started.

## Objective

Creating a route copies a template route into it. Today that template is an
11 MB archive downloaded from koniec.org, and most of it is stock MSTS
content. Replace every file of it with TSRE's own: generated by TSRE code
when a route is created, written by us, or taken from our asset library
(tasks 01 and 02). Then the template moves into the TSRE git repository and
the download goes away.

**The rule:** no stock MSTS file, and no file derived from one, may stay. A
file is replaced or removed even when it is only a trimmed or edited copy,
and even when it has no stock counterpart but carries a stock name or comes
from the same archive (origin unknown). Nothing from the template goes into
git until the whole template follows this rule.

## Ways to replace a file

1. **Generated by TSRE code** at route creation, as `graphic.ace` is: a
   function per file (or family) in `RouteCreator` or a helper next to it,
   drawing a `QImage` and writing `.ace` with `AceLib::save`. For plain
   images: sky gradients, star field, sun and moon discs, rain and snow
   sprites, water layers (noise), the terrain patch and detail textures,
   shadow gradients, light glows, digit atlases drawn with a font. Sizes
   and layouts follow what the reading code and the `.env`, `speedpost` and
   `sigcfg` files expect.
2. **Written by us**: data and `.env` files rewritten from the format
   (`docs/features/` and the readers in `src/tsre`), not edited copies.
   Files whose content depends on the chosen assets (the ref file,
   `speedpost.dat`, `sigcfg.dat`) are better generated by code from one
   list of assets.
3. **Our assets** from `/home/arch/NetBeansProjects/assets-gen` (task 01,
   task 02 for the tree), with their generator scripts. Textures read by
   GLOBAL shapes keep their file names and their layout (texture
   coordinates of those shapes: check a capture of a GLOBAL track, road and
   tunnel shape with the new texture). Shapes are in the format the reader
   needs: where only MSTS `.s` works (signals, speed posts, telegraph pole,
   car spawner, forest tree in Open Rails), write `.s` as text
   (`docs/features/msts-shape-file-format.md`); `--shapeconv` only
   re-encodes existing `.s` files. Signals can be a simpler set than the
   Japanese one, but the ones in `sigcfg` must work in TSRE and Open Rails.

## Steps

1. **Remove the unused files** (5.5 MB) and the broken references from
   `RouteCreator`'s lists and the data files. Create a route and check that
   it loads. Report, with an answer proposed for every open question below,
   then stop for review.
2. **Generated textures** (way 1) and **written data and `.env` files**
   (way 2), with the generated files written at route creation and no
   longer copied.
3. **Own assets** (way 3) for track, road, tunnel, buffer and crossing
   textures, signals, posts, telegraph pole, car and tree. Coordinate with
   task 01 (assets-gen); those assets also count for the library there.
4. **Into the repository**: the remaining template files (own assets, text)
   go into the repo with a manifest (below); `RouteCreator` reads them from
   there, `LoadWindow::downloadTemplateRoute` and the koniec.org URL go,
   `templateResourcesAvailable` checks the new location.

## Manifest and provenance check

The template in the repo has a `MANIFEST.md`: one line per file with how it
is made (the generating function, the asset and its generator script, or
"written by hand"). A script in the task's work (kept with the template, for
example `scripts/check-template-provenance.py`) compares every file of the
template and of a newly created route with every file under
`/home/arch/ORTS/MSTS/ROUTES` and `GLOBAL` by content, and fails on any
match. The check runs before the commit that adds the template to git.

## Checking

- `--test --test-suite=new-route` passes, with its expectations updated to
  the new template.
- A route created with the GUI (on a copy of the game root) loads in TSRE:
  terrain with its default texture, water, sky; placing a dynamic track, a
  GLOBAL track and road shape, a signal, a speed post and milepost, a
  telegraph pole line, a forest, a car spawner and the ref file's objects
  works and draws with the new textures. Captures (`renderer-capture`) of
  these, compared with the same placements on the old template, for review.
- The created route loads in Open Rails if it is available on this machine;
  otherwise list what needs checking there.
- The provenance check passes.

## Open questions (for review after step 1)

- Sounds: `ttype.dat` and `ssource.dat` point at MSTS's own `SOUND` files,
  and `ingame.sms` at files the template lacks. Keep references to files of
  an MSTS installation, ship our own sounds, or leave them out (does Open
  Rails need them)?
- Hazards (`deer.haz`, `spotter.haz`): keep with our own content, or drop
  them if Open Rails does without?
- Signals: which signal system for the default set (Polish, a generic
  one)?
- Where the template lives in the repo (for example under `appdata`, which
  is partly tracked) and how it reaches users' installs.

## Acceptance

- Every file a new route gets is generated by TSRE code, written by us, or
  one of our assets, as listed in the template's `MANIFEST.md`.
- The provenance check finds no stock file in the template or in a new
  route.
- No download is needed to create a route.
- `new-route` passes; a new route loads and the editor's placement tools
  work on it as listed under Checking.
