# Task 03 - Own Template Route

Status: ready; not started.

## Objective

Creating a route copies a template route into it. Today that template is an
11 MB archive downloaded from koniec.org, and most of it is stock MSTS
content. Replace its assets with TSRE's own: generated by TSRE code when a
route is created, or taken from our asset library (tasks 01 and 02), and
rework its text data files. Then the template moves into the TSRE git
repository and the download goes away.

**The rule:**

- Assets (textures, shapes, sounds): no stock MSTS file, and no file derived
  from one, may stay. A file is replaced or removed even when it is only an
  edited copy, and even when it has no stock counterpart but carries a stock
  name or comes from the same archive (origin unknown).
- Text data files (`.dat`, `.haz`, `.env`, `.ref`, `.sms` definitions) are
  minimal and serve as examples of their formats, not as assets: keep them as
  the base and rework them. Remove the Japanese and other stock-specific
  entries and names, point every reference at our assets, and leave only
  what a new route needs.
- Nothing from the template goes into git until the whole template follows
  this rule.

## Ways to replace a file

1. **Generated by TSRE code** at route creation, as `graphic.ace` is: a
   function per file (or family) in `RouteCreator` or a helper next to it,
   drawing a `QImage` and writing `.ace` with `AceLib::save`. For plain
   images: sky gradients, star field, sun and moon discs, rain and snow
   sprites, water layers (noise), the terrain patch and detail textures,
   shadow gradients, light glows, digit atlases drawn with a font. Sizes
   and layouts follow what the reading code and the `.env`, `speedpost` and
   `sigcfg` files expect.
2. **Reworked text data**: the data, `.env`, `.haz` and `.sms` files stay
   as the base (format examples) and are cleaned up: no `JP`/`jp1`/`jp2`
   or other stock names, entries reduced to what a new route needs,
   references pointing at our assets. The readers in `src/tsre` and
   `docs/features/` show which entries matter. Files whose content follows
   from the chosen assets (the ref file, `speedpost.dat`, `sigcfg.dat`) may
   instead be generated by code from one list of assets.
3. **Our assets** from `/home/arch/NetBeansProjects/assets-gen` (task 01,
   task 02 for the tree), with their generator scripts. Textures read by
   GLOBAL shapes keep their file names and their layout (texture
   coordinates of those shapes: check a capture of a GLOBAL track, road and
   tunnel shape with the new texture). Signals can be a simpler set than
   the Japanese one, but the ones in `sigcfg` must work in TSRE and Open
   Rails.

   Shapes are in the format the reader needs; where that is MSTS `.s`
   (signals, speed posts, telegraph pole, car spawner, forest tree in Open
   Rails), make `.s` files one of these ways
   (`docs/features/msts-shape-file-format.md`; `--shapeconv` only
   re-encodes existing `.s` files):
   - by hand, as text, for the simplest shapes;
   - with a simple OBJ to `.s` converter written for this (in assets-gen's
     `tools/`), so the generators that already write OBJ can make `.s`;
   - with Blender through its MCP server and an `.s` export plugin, for
     shapes that need modelling.

## Steps

1. **Check every file's use**: for each file, what reads it (TSRE code,
   Open Rails, MSTS conventions, other template files) and which way it is
   replaced, with special care for the "no reference found" ones (above).
   Report a table of file, users, proposed action (generate, rework, own
   asset, remove) and a proposed answer to every open question below, then
   stop for review. Nothing is removed or replaced in this step.
2. **Generated textures** (way 1) and **reworked text data** (way 2), with
   the generated files written at route creation and no longer copied.
3. **Own assets** (way 3) for track, road, tunnel, buffer and crossing
   textures, signals, posts, telegraph pole, car and tree, and for any
   "no reference found" file step 1 shows to be needed. Coordinate with
   task 01 (assets-gen); those assets also count for the library there.
4. **Remove** what step 1 showed to be unused and the review confirmed,
   with `RouteCreator`'s lists and the broken references (above). Create a
   route and check that it loads.
5. **Into the repository**: the remaining template files (own assets, text)
   go into the repo with a manifest (below); `RouteCreator` reads them from
   there, `LoadWindow::downloadTemplateRoute` and the koniec.org URL go,
   `templateResourcesAvailable` checks the new location.

## Manifest and provenance check

The template in the repo has a `MANIFEST.md`: one line per file with how it
is made (the generating function, the asset and its generator script, or
"reworked format example" for text data). A script in the task's work (kept
with the template, for example `scripts/check-template-provenance.py`)
compares every asset file (textures, shapes, sounds) of the template and of
a newly created route with every file under `/home/arch/ORTS/MSTS/ROUTES`
and `GLOBAL` by content, and fails on any match. Text data files are not
compared; a reviewer reads their diff against the old template instead. The
check runs before the commit that adds the template to git.

## Checking

- `--test --test-suite=new-route` passes, with its expectations updated to
  the new template.
- A route created with the GUI (on a copy of the game root) loads in TSRE:
  terrain with its default texture, water, sky; placing a dynamic track, a
  GLOBAL track and road shape, a signal, a speed post and milepost, a
  telegraph pole line, a forest, a car spawner and the ref file's objects
  works and draws with the new textures. Captures (`renderer-capture`) of
  these, compared with the same placements on the old template, for review.
- The created route loads in Open Rails if it is available on this machine;
  otherwise list what needs checking there.
- The provenance check passes.

## Open questions (for review after step 1)

- Sounds: `ttype.dat` and `ssource.dat` point at MSTS's own `SOUND` files,
  and `ingame.sms` at `.wav` files the template lacks. Keep references to
  files of an MSTS installation, ship our own sounds, or leave them out
  (does Open Rails need them)?
- Signals: which signal system for the default set (Polish, a generic
  one)?
- Where the template lives in the repo (for example under `appdata`, which
  is partly tracked) and how it reaches users' installs.

## Acceptance

- Every file a new route gets is generated by TSRE code, one of our
  assets, or a reworked text data file, as listed in the template's
  `MANIFEST.md`.
- The provenance check finds no stock asset in the template or in a new
  route; the reworked text data files have no stock-specific names left.
- No download is needed to create a route.
- `new-route` passes; a new route loads and the editor's placement tools
  work on it as listed under Checking.
