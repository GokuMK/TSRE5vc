Open Rails feature review

TrProfile extension proposal

A backward-compatible format proposal for profile families, object roles, path-frame control and minimal OBJ-based 3D template geometry. TSRE provides the working reference implementation.

Audience: Open Rails maintainers · Reference branch: feature/trprofile-3d-mesh · September 2026
Contents 1. Review summary2. Scope and status3. Files and families4. ObjectType5. Role selection6. PathFrameMode7. Template3D8. Generation modes9. Placement10. GeometryMode11. Complete examples12. ORTS implementation13. Coordinates and UVs14. Compatibility15. Reference evidence

1. Review summary

This proposal extends the existing Open Rails TrProfile format instead of introducing a TSRE-only procedural format. Existing polyline profiles and material rules remain the baseline. New attributes describe profile families and complete 3D geometry that cannot be represented as a cross-section alone.

No replacement formatLOD, LODItem, Polyline, Vertex, materials, chord controls and matching filters remain valid.
Small data-model additionsObjectType, role variants, PathFrameMode and Template3D are added to the existing hierarchy.
Working referenceTSRE parses, selects and renders the proposal for static track, dynamic track, roads and Ruler paths.
Requested decision: accept the file-format direction and semantics. The TSRE implementation is evidence that the model is practical; its OpenGL/OglObj details are not proposed as ORTS architecture.

3. Files, discovery and profile families

Profiles are loaded from the active route’s TRACKPROFILES directory. Files with the same stem and both .stf and .xml extensions resolve to XML; other files are read in case-insensitive filename order.

The filename stem is the family identity. Name is descriptive text and does not change lookup identity.

Identity exampleRdProfile.stf → family “RdProfile” → RdProfile, RdProfile_left, RdProfile_middle, RdProfile_right, RdProfile_single

Multiple profiles in one STF file NEW

An STF file may contain several top-level TrProfile blocks. This keeps all role variants of one family together.

# RdProfile.stf
TrProfile (
    ObjectType ( ROAD MAIN )
    Name ( "Default road" )
    # ...
)

TrProfile (
    ObjectType ( ROAD LEFT )
    Name ( "Default road — left lane" )
    # ...
)
RuleBehavior
STF rootsOne or more TrProfile ( ... ) blocks.
XMLOne profile per file. There is no multi-root XML wrapper yet.
Catalog keyObjectType + filename family + role, compared case-insensitively.
Duplicate identityThe later profile is ignored and a diagnostic is recorded.
Invalid profileNot inserted into the catalog; parser diagnostics remain available.

4. ObjectType NEW

ObjectType identifies the consumer and, optionally, the member’s role in a family.

ObjectType ( ROAD LEFT )

Compatibility default: if ObjectType is absent, the profile is TRACK MAIN.

5. Multi-path role selection NEW

Static TrackObj shapes may contain several paths. When the selected profile is MAIN, TSRE assigns family roles per group of paths facing the same direction.

  1. Group consecutive paths whose rotation differs by no more than 0.1°.
  2. For a group containing more than one path, assign LEFT to the first, RIGHT to the last and MIDDLE to every path between them.
  3. If the requested role is missing, fall back to MAIN.
  4. If the user selected SINGLE, use it unchanged for every path.
# Three parallel paths:
path 0  →  LEFT
path 1  →  MIDDLE
path 2  →  RIGHT

# Two crossing two-path roads:
group A →  LEFT, RIGHT
group B →  LEFT, RIGHT

7. Template3D NEW

A Template3D entry loads one or more route-local OBJ meshes and either deforms or places them along the same path used by polylines. It is a child of LODItem, so the LOD item supplies texture, shader, alpha-test and texture-address settings.

Template3D (
    GenerationMode   ( Repeat )
    GeometryMode     ( Baked )
    ShapeSelectionMode ( Cycle )
    Shape ( "meshes/tie-a.obj" )
    Shape ( "meshes/tie-b.obj" )
    Offset  ( 0 0 0 )
    Spacing ( 0.65 )
    Phase   ( 0 )
)

Supported OBJ subset: v, vt, vn and triangular f v/vt/vn records with positive indices. OBJ materials are ignored. Unknown directives and ordinary whitespace are accepted.

8. Generation modes

Sweep

Tiles an OBJ’s authored Z depth along every path span, trims the last copy, deforms all vertices through sampled path frames and advances longitudinal V with path distance.

Stretch

Maps one complete OBJ between two authored endpoints. On Rulers this means one copy per original span; averaged node frames keep offset geometry joined at corners.

Repeat

Places rigid copies at Phase + n × Spacing. Best for simple frequent objects such as sleepers.

Place

Places rigid copies at semantic path locations. Requires at least one Placement entry.

ModeGeometryLongitudinal UVShared allowed
SweepDeformed and tiledAdvanced by travelled path lengthNo
StretchDeformed once per path/spanAuthored UV preservedNo

9. Placement NEW

SyntaxPlacement ( Start|End|Both|Nodes AlongPath|AgainstPath|Outward|Inward )

Location chooses where the object is placed and which base frame is used. Facing optionally reverses that frame.

LocationPoint ownershipOrientation
StartOnce at every span start.Direction of that span.
EndOnce at every span end.Direction of that span.
BothExpands to Start and End for every span.Each endpoint remains aligned with its span.
NodesOnce at every unique authored Ruler node.First/last use their only adjacent span. Internal nodes use the angular bisector of incoming and outgoing directions.
FacingBehaviorValid with Nodes
AlongPathUse the selected frame as-is.Yes
AgainstPathRotate the rigid object 180° around its up axis.Yes
OutwardStart faces backward; End faces forward.No—ambiguous at internal nodes
InwardStart faces forward; End faces backward.No—ambiguous at internal nodes
Template3D (
    GenerationMode ( Place )
    GeometryMode   ( Shared )
    Shape          ( "meshes/pole.obj" )
    Placement      ( Nodes AlongPath )
)
Stretch and Nodes match: multiline Stretch interpolates the same averaged node frames. Wires and other offset geometry therefore arrive at the same orientation used by a pole placed with Nodes.

10. GeometryMode NEW

ValueStorageRecommended use
BakedEvery generated occurrence is copied into a material vertex buffer.Default. Dense, simple and frequent geometry such as sleepers.
SharedOne source mesh plus a transform matrix for every occurrence.Complex rigid objects such as catenary poles.

Shared is rejected for Sweep and Stretch because those modes deform the source mesh. The current shared-instance render path is implemented for RulerObj. TrackObj and DynTrackObj generation remains baked.

Not GPU instancing yet: shared mode reduces generated vertices and CPU mesh construction, but TSRE currently submits an ordinary transformed draw for each occurrence.

Multiline wire and shared poles

TrProfile (
    ObjectType ( STATIC MAIN )
    Name ( "50 m catenary" )
    LODMethod ( ComponentAdditive )

    LOD (
        CutoffRadius ( 3000 )
        LODItem (
            TexName ( "wire.png" )
            PathFrameMode ( NoRoll )

            # One wire mesh is stretched across every authored Ruler span.

                GenerationMode ( Stretch )
                ShapeSelectionMode ( ByObject )

            # Every unique node receives one pole in the matching node frame.

                GenerationMode ( Place )
                GeometryMode ( Shared )

                Placement ( Nodes AlongPath )
            )
        )
    )
)

12. Minimal ORTS implementation

The proposal can be implemented by extending the existing TrProfile loader and procedural-track path. It does not require a general OBJ renderer, a replacement shape system or world-space generated meshes.

  1. Extend profile discovery. Enumerate supported files in TrackProfiles, recognize RdProfile as the default road family and allow multiple top-level STF TrProfile blocks.
  2. Extend the parsed model. Add ObjectType and role, PathFrameMode on LODItem, and a collection of Template3D children beside Polyline.
  3. Resolve family roles before generation. Split TrackShape paths into consecutive same-direction groups, then select LEFT/MIDDLE/RIGHT with MAIN fallback. SINGLE bypasses expansion.
  4. Load only the required OBJ subset. Parse positions, UVs, normals and positive-index triangular faces. Ignore materials and unrelated directives because the parent LODItem remains the material authority.
  5. Generate through existing path frames. Polyline and Template3D consume the same sampled track or Ruler path. Apply PathFrameMode before emitting vertices or rigid transforms.
  6. Preserve the current path. A LODItem containing only Polyline data must continue through the existing ORTS implementation without changed output.

Suggested ownership

ConcernMinimal ORTS changeWhat should remain unchanged

Porting boundary: copy the file-format semantics and generated result, not TSRE's OpenGL classes. In particular, ORTS should use its native MSTS coordinate convention and its existing procedural-track frames.

Acceptance tests for an ORTS port

  • An unchanged legacy polyline profile produces the same geometry as before.
  • One STF file loads MAIN, LEFT, MIDDLE, RIGHT and SINGLE family members.
  • A two-path group resolves LEFT/RIGHT; a three-path group resolves LEFT/MIDDLE/RIGHT; two crossing pairs resolve LEFT/RIGHT twice.
  • Sweep follows a curved and graded section with continuous longitudinal UVs.
  • Repeat respects Spacing and Phase; Place respects endpoint facing.
  • A three-node Ruler places three Nodes objects and uses the direction bisector at the middle node.
  • NoRoll and Upright change only the requested frame components.

13. Coordinates, frames and UVs

Profile coordinate convention

  • Units are metres.
  • +X is right.
  • +Y is up.
  • −Z is forward in MSTS/ORTS profile and OBJ data.

This is already the native authored convention for MSTS/ORTS data. An ORTS implementation should keep it. The TSRE reference converts the complete basis only because its renderer uses OpenGL-style local +Z; that conversion must not be copied into ORTS.

Template3D source convention

  • Sweep and Stretch meshes begin at Z=0 and extend toward negative Z.
  • Offset is expressed in the authored OBJ basis.
  • Normals and UV indices are mandatory for every triangular face.

Texture behavior

GeometryUV behavior
PolylineBase UV plus DeltaTexCoord × path distance.
Template3D SweepU is preserved; V advances continuously with travelled path distance.
Stretch / Repeat / PlaceAuthored OBJ UVs are preserved.

14. Compatibility and limitations

Compatibility

  • Existing Polyline-only STF and XML profiles retain their behavior.
  • Missing ObjectType means TRACK MAIN.
  • Missing PathFrameMode means Full.
  • Missing GeometryMode means Baked.
  • Role variants are optional; a missing requested role falls back to MAIN.
  • A profile containing no Template3D follows the existing Polyline path.

Proposed format limits

  • Multiple top-level profiles and Template3D are initially STF-only. XML remains one profile per file until a wrapper representation is agreed.
  • The OBJ subset accepts only positive-index triangular v/vt/vn faces and deliberately ignores materials.
  • Sweep and Stretch require baked/deformed output; Shared is valid only for Repeat and Place.
  • One Stretch entry spans exactly one semantic input span. It is not automatically subdivided for LOD because subdivision would change its defined result.

TSRE reference limitations, not format requirements

  • Shared output currently benefits RulerObj; TSRE TrackObj and DynTrackObj remain baked.
  • TSRE shared rendering reuses geometry but does not issue a hardware-instanced draw call.
  • TSRE uses a temporary 10 cm mesh overlap to conceal sharp grade seams without changing database endpoints.
  • The older experimental shapetemplates.dat reader is disabled in the reference branch but has not yet been removed.
