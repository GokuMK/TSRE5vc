TSRE format and Open Rails implementation reference

Procedural terrain materials

An editable categorical material map for each terrain tile, route-wide source definitions, seasonal textures and a conventional baked fallback for legacy applications.

1. Format summary

Procedural terrain stores which material covers every location, not a pre-composed color image. TSRE keeps that categorical data editable and generates detailed patch textures. A normal MSTS terrain texture remains saved beside it for applications that do not understand the extension.

Route-wide materialsterrainmaterials.dat assigns stable UiDs to source textures and display names.
Tile-local IDsA compressed square .pmap stores one byte per sample; TSRE and the Open Rails branch accept 2048-8192, while new TSRE maps default to 4096.
Compatible fallbackOrdinary terrain shaders, patch UVs and baked ACE textures continue to render in MSTS and older tools.
Design rule: procedural data is optional. Missing, malformed or unsupported extension data must never prevent the conventional baked terrain from rendering.

3. Material catalogue

terrainmaterials.dat is UTF-16 text with a BOM and MSTS-style blocks. Version 1 stores stable identity, a display name and a primary texture, with optional per-material detail texture and scale.

        DetailScale ( 32 )

FieldRule
VersionRequired; currently exactly 1.
NextUiDRequired, nonzero and greater than every allocated UiD. Deleted identities are not reused.
UiDPositive uint32 route identity, independent of list order and tile-local IDs.
NameNonempty author-facing text; never used as lookup identity.

DetailTextureOptional safe relative detail texture. Missing means microtex.ace.
DetailScaleOptional finite positive repeat scale. Missing means 32.
Renderer status: the TSRE Gather renderer and the Open Rails direct renderer use these per-material detail fields. TSRE's retained CPU near path still uses fixed microtex.ace/32 when selected through the internal recovery switch. Rotation, base-texture physical scale, mixing policy and per-season filenames remain outside this definition.

4. Terrain-tile extension

The binary .t descriptor keeps the normal MSTS children and adds one terrain-level container. The extension was moved out of terrain_samples because older Open Rails readers reject unknown children there but safely skip an unknown terrain-level block.

terrain
  terrain_samples                  # unchanged MSTS data
  terrain_shaders                  # baked-fallback material
  terrain_patches                  # unchanged patch records
  TSRETerrainMaterials             0x00061004
    TSRETerrainMaterialBuffer       0x00061000
    TSRETerrainMaterialMap          0x00061002
    TSRETerrainBakedMaterials      0x00061003
TokenPayloadMeaning
TSRETerrainMaterialsChild blocksOuter extension container; no extra version or count.
TSRETerrainMaterialBufferUTF-16 stringSafe tile-relative .pmap filename.
TSRETerrainMaterialMapCount and uint32 pairsMaps each local byte ID to a nonzero route material UiD; at most 256 entries.

Older sample-level placement remains readable by TSRE for migration. Saving emits only the terrain-level container. Mixed or duplicate known definitions are refused rather than guessed.

5. The .pmap material plane

Version 1 is a zlib-compressed square byte image. Every decoded byte is a tile-local material ID. It is categorical data: values must never be linearly interpolated as colors. TSRE and the experimental Open Rails reader accept square powers of two from 2048 through 8192. TSRE preserves the loaded authoring size; new maps default to 4096. Open Rails may reduce the effective runtime map categorically for the active feature level.

OffsetSizeValue

# Conceptual decoded data
byte localMaterialId[height][width]

# Tile-local to route-wide identity
0 -> UiD 7  # ploughed field
1 -> UiD 2  # grass
2 -> UiD 4  # city ground

Why local bytes?

The dense editable plane uses one byte per sample: 4 MiB at 2048, 16 MiB at 4096 and 64 MiB at 8192, independently of route catalogue size. A tile normally uses only a small subset of route materials.

Why stable UiDs?

Renaming or reordering the route catalogue cannot silently reinterpret painted terrain. Cross-route copying must explicitly reconcile identities.

6. Rendering model

TSRE editor

TSRE keeps the native-resolution ID map available for painting and uploads it as an 8-bit categorical texture. Near patches draw the referenced source materials directly; save also produces an opaque 1024-square DXT1 baked tile texture. A missing bake recipe is normally generated at twice its final patch-region size and reduced with one 2 x 2 color average. The former CPU near renderer and full detailed-output regeneration remain selectable in code for comparison and recovery tests.

  1. Resolve local ID through the tile table to a route material UiD.
  2. Resolve the material source for the selected season or weather variant.
  3. Use deterministic categorical scattering at boundaries; never blend numeric IDs.
  4. Draw every distinct material referenced by a near patch and its sampling halo.
  5. Use the saved baked terrain outside the detailed distance and in legacy applications.
Authoring accuracy is intentionally uncapped: TSRE imposes no artificial material-pass limit per patch. A pathological patch can therefore be slower, but the editor continues to show every authored material. The byte map's natural upper bound is 256 IDs.

Boundary sampling

At a transition, four neighboring categorical samples contribute weights. A deterministic position-derived value chooses one material according to those weights. This produces a scattered edge without inventing an invalid material ID between two integers.

The ID map and the color texture have different jobs: the map preserves editable identity; generated and baked images are disposable rendering products.

7. Seasonal source selection

One painted map is shared by every season. Material filenames do not change; the active implementation selects a directory for each source independently and falls back when that individual file is missing.

Summer / baseTERRTEX—
Clear springTERRTEX/SPRINGTERRTEX
Clear autumnTERRTEX/AUTUMNTERRTEX
Winter or snowy spring/autumnTERRTEX/SNOWTERRTEX

The Open Rails branch applies this feature-scoped policy consistently to detailed sources, the baked fallback, microtexture and mapped tiles outside the detailed area. Ordinary non-procedural MSTS terrain keeps the existing Open Rails resolver.

TSRE supports more authored variants: clear, rain and snow directories for all four seasons, plus route-wide batch baking. Those additional precipitation variants are deliberately outside the first Open Rails patch.

8. TSRE authoring workflow

  1. Add or choose a route material in the F2 procedural material list. Importing an image copies it to route TERRTEX only when required and immediately saves a stable catalogue entry. Existing byte-identical files are reused; a suffix is created only for different content with the same filename.
  2. Enable procedural materials on a tile. The selected route material initializes the complete map.
  3. Paint material IDs, fill a patch or flood-fill a connected region. Picking restores the route material identity.
  4. Save the route. TSRE atomically writes the map, descriptor metadata and current baked fallback, retaining recovery backups on failure.
  5. Optionally batch-bake all saved procedural tiles for available seasonal variants.
# CPU-only route-wide seasonal bake
TSRE5vc.exe --refreshpmaptextures
  --route "C:\MSTS\ROUTES\procedural"
  --season all
  --res 1024
  --patch-res 512

Undo snapshots the tile's ID map and mapping state once per terrain action. Route catalogue additions and renames are reusable route-data changes, not terrain brush undo records.

9. Compatibility contract

ConsumerBehavior
MSTS / extension-unaware editorIgnores the terrain-level extension and displays the conventional baked shader and ACE texture.
Unmodified Open RailsSkips the unknown terrain-level container and renders the baked fallback. Keeping the extension outside terrain_samples is essential.
TSRELoads, edits and saves the map, catalogue mapping and bake metadata; generates detailed and compatibility textures.
Procedural Open Rails branchReads the extension and route catalogue, directly renders selected source textures nearby, and retains the baked texture everywhere else.

Unsupported versions, unsafe paths, duplicate mappings, truncated zlib streams and unresolved UiDs disable procedural detail for the affected data. They do not erase or replace the saved fallback.

Binary-token prerequisite: the assigned tokens use full namespaced SIMIS IDs. The Open Rails implementation is stacked on the native-token-ID parser work; low-16-bit aliases are intentionally not used.

10. Open Rails direct renderer

The Open Rails implementation does not port TSRE's CPU image generator. It uploads the categorical map and draws bounded masked material passes. This preserves full source-texture resolution and avoids adding an editor-oriented decode, composition and BC1-writing pipeline to the simulator.

  1. Parse terrainmaterials.dat once for the route and validate the tile extension.
  2. Bounded-decompress the .pmap, categorically reduce it when required by the feature level, and count effective-map material coverage per terrain patch with a one-texel boundary halo.
  3. Sort materials by covered area and load no more than 32 source textures for the tile, including each selected material's detail texture.
  4. Upload the effective 2048, 4096 or 8192-square map as an Alpha8 GPU texture and share one deterministic 2048-square Alpha8 noise texture.
  5. For every patch, draw no more than five detailed material passes. If anything is missing or omitted, draw the baked patch first so no pixels become holes.
// Simplified per-patch decision
candidates = sortByCoveredArea(mapIds);
layers = availableSources(candidates).take(5);
useBakedBase = layers.count != candidates.count;

Detailed procedural maps are currently restricted to mapped high-resolution tiles in the camera's 3 x 3 tile neighborhood. Mapped outer tiles, low-resolution terrain and distant mountains use the saved fallback. Generated map and noise textures participate in the existing texture manager's mark/sweep lifetime.

Shader behavior

Level 9.3 uses four-neighbor stochastic categorical selection. Level 9.1 uses a point-selected fallback and omits procedural microtexture to stay within its instruction limit. Level 9.1 caps the effective map at 2048, Level 9.3 at 4096 and Level 10.0 permits 8192. Every surviving opaque material pixel writes terrain depth; this prevents terrain submitted later from showing through mountains.

11. Explicit limits and fallback

LimitCurrent valueFallback behavior
Detailed neighborhood3 x 3 high-resolution tilesOuter mapped tiles render their saved baked textures.
Detailed source textures32 per tileMaterials beyond the limit remain represented by the baked base.
Detailed materials5 per patchLargest available areas render directly; omitted areas retain the bake.
Decoded mapSquare power of two, 2048-8192 in TSRE and Open RailsWrong headers, dimensions, expansion length or oversized files disable procedural detail.
Noise textureOne shared 2048 x 2048 Alpha8 textureDeterministic and managed with other generated textures.

A pathological patch may reference 20 or all 256 byte IDs. Rendering cost remains bounded: material areas are sorted, only configured detailed layers are drawn, and the remaining pixels keep the bake. The renderer never assigns omitted pixels to an unrelated source.

TSRE differs deliberately: the five-material patch cap and 32-source tile cap above belong to the Open Rails runtime renderer. TSRE renders all available materials referenced by each patch so route authors can inspect the true result, accepting lower editor frame rate for extreme content.
